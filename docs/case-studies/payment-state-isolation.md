# 결제 상태와 외부 전송 실패의 분리

> **실무 설계 사례의 공개용 재구성입니다.** 회사 소스 코드·DB 구조·고객 식별 정보·원본 로그는 포함하지 않습니다. 아래 상태명과 도식은 개념 설명용이며 실제 운영 코드의 클래스·테이블명과 일치한다는 의미가 아닙니다.

## 문제

무인 결제 게이트웨이는 VAN 카드 승인과 내부 결제 결과를 처리하고, 이후 외부 본사 API에 결제 정보를 전달해야 했습니다. 외부 API가 오류를 반환하거나 응답하지 않는 경우에도 이미 확정된 결제 사실을 잘못 취소하거나 실패로 바꿔서는 안 됩니다.

외부 응답이 지연되면 동기 요청을 처리하는 서버의 워커와 데이터베이스 연결이 오래 점유될 수 있다는 운영상 문제도 있었습니다.

## 지켜야 할 불변식

**검증·확정된 내부 결제 상태는 후속 본사 송신의 성공 여부와 독립적입니다.**

다음은 실제 스키마가 아닌 개념 모델입니다.

```text
VAN 승인 결과 검증
        |
        v
내부 결제 확정 ----------------------> 내부 결제 결과 유지
        |
        v
본사 API 송신 시도
        |
        +-- 성공 --> 송신 성공 기록
        |
        +-- 실패 --> 송신 실패 기록 + 요청/응답 감사 기록
                     (내부 결제 확정은 변경하지 않음)
```

결제 완료와 외부 전달 완료는 서로 다른 사건입니다. 외부 API의 응답 상태를 결제의 유일한 진실 원천으로 사용하지 않는 것이 핵심입니다.

## 설계 결정

| 선택지 | 장점 | 위험 또는 이유 |
| :--- | :--- | :--- |
| 본사 API 성공 후에만 결제 확정 | 외부 수신 확인을 성공 조건에 포함 가능 | 외부 장애가 정상 VAN 승인 이후의 내부 매출 확정에 영향을 미침 |
| **결제 확정과 송신 결과 분리** | 외부 장애를 별도 실패 영역으로 격리 | 송신 실패 건의 후속 추적·처리가 별도로 필요 |
| 내구성 있는 큐와 자동 재전송 | 최종 전달 보장에 가까워질 수 있음 | 당시 시스템의 실제 구현 범위를 넘어섬 |

실제 적용한 접근은 **내부 상태를 보존하고 송신 결과를 별도로 기록하는 것**입니다. 외부 무응답으로 인한 자원 점유를 제한하기 위해 HTTP 연결 2초·전체 요청 5초의 타임아웃을 두었습니다.

## 어떤 실패를 어떻게 다루는가

| 상황 | 기대 동작 |
| :--- | :--- |
| VAN 승인 검증 실패 | 결제 확정을 진행하지 않음 |
| VAN 승인 검증 및 내부 결제 확정 후 본사 API 성공 | 확정 상태 유지, 송신 성공 기록 |
| VAN 승인 검증 및 내부 결제 확정 후 본사 API 오류 | 확정 상태 유지, 송신 실패·감사 기록 |
| 본사 API 응답 지연·무응답 | 제한된 대기 후 실패 기록, 내부 확정 상태 유지 |

이 표는 설계 계약의 요약이며 공개 저장소에서 실행할 수 있는 테스트 결과표는 아닙니다.

## 검증 범위와 한계

- 과거 실제 운영 데이터 점검에서 결제 완료 후 본사 송신 실패에도 내부 결제 상태가 유지된 사례를 확인했습니다. 고객 정보·원본 DB·로그는 공개하지 않습니다.
- 송신 상태 분리가 **본사의 최종 수신을 보장하는 것은 아닙니다.** 당시 구현에는 내구성 있는 비동기 큐와 자동 재송신이 없었습니다.
- 내부 상태 분리와 타임아웃 도입을 근거 없이 전체 응답시간 개선율이나 결제 성공률 향상으로 표현하지 않습니다.
- 이 문서는 운영 현장의 기술적 판단을 설명하는 사례이며 **공개 Java/Spring 샘플 코드나 독립 CI 테스트를 제공하지 않습니다.**

## 이 경험에서 중요했던 점

외부 연동은 내부 비즈니스 사실을 자동으로 뒤집을 권한을 가져서는 안 됩니다. 요청 성공과 비즈니스 완료의 정의를 구분하고, 부분 실패를 정식 상태로 다룰 때 장애의 영향 범위를 설명할 수 있습니다.
