# AI 고객상담: 권한 경계와 근거 기반 응답

> **실무 설계 사례의 공개용 재구성입니다.** 소스 코드·내부 권한 API·고객 데이터·비공개 KB는 포함하지 않습니다. 실제 구축은 회사 내부의 제한된 **STG 파일럿** 기준이며, 대규모 상용 운영 성과로 표현하지 않습니다.

## 1. 매장 존재와 사용자 소속은 다른 사실

### 관측된 문제

매장 정보 조회의 `found` 결과가 **매장이 존재한다는 사실**과 **사용자가 그 매장에 소속되어 있다는 사실**을 혼동하도록 사용되는 경로가 있었습니다.

두 가지는 서로 다른 계약입니다.

```text
사용자 식별
   |
   +-- 매장 프로필 조회 --------> 매장이 존재하는가? (조회 정보)
   |
   +-- 사용자-매장 소속 판정 --> 이 사용자가 접근할 수 있는가? (인가 정보)
                                  |
                                  +-- 확인됨: 해당 범위만 허용
                                  +-- 비소속/판정 불가: 거부
```

### 선택한 방식

- 프로필 조회와 소속 판정의 서버 계약을 분리했습니다.
- 매장 존재만으로 사용자 세션에 권한을 부여하지 않도록 했습니다.
- 소속 판정에 필요한 신뢰 가능한 결과를 얻지 못하면 접근을 허용하지 않는 **fail-closed 인가**를 적용했습니다.

### 검증과 비용

비소속 매장을 허용하던 재현 사례를 수정하고, 소속·비소속·식별 정보 누락·조회 오류를 구분하는 회귀 검증을 구성했습니다.

대신 소속 판정 API 장애가 정상 사용자의 가용성에 영향을 미칠 수 있습니다. 보안 경계를 강화하면 외부 의존성의 가용성 비용이 생긴다는 점까지 설계의 일부로 봅니다.

## 2. 모델이 그럴듯하게 설명한다고 근거가 생기는 것은 아니다

### 관측된 문제

지식 베이스에 근거가 없는 오류코드에 대해 LLM이 그럴듯한 원인과 조치를 만들어 낼 수 있었습니다. 그럴듯한 문장을 생성한 사실은 해당 답변이 올바르다는 증거가 아닙니다.

### 선택한 방식

명시된 오류코드는 응답 생성 전에 활성 지식 베이스에 근거가 존재하는지 확인합니다. 근거를 확인하지 못한 코드에 대해 사실처럼 설명하기보다 증상 등 추가 정보를 요청하도록 분기했습니다.

```text
사용자 질문
   |
   +-- 명시적 오류코드 없음 ------> 기존 상담 흐름
   |
   +-- 명시적 오류코드 있음
           |
           v
       활성 KB 확인
           |
           +-- 근거 있음 --------> 근거 기반 답변 흐름
           |
           +-- 근거 없음 --------> 근거 없는 원인·조치 단정 차단
```

### 검증과 한계

지원되는 코드와 지원되지 않는 코드, 코드 누락 및 지식 베이스 조회 실패를 구분하는 테스트를 작성했습니다.

**중요한 한계:** KB 조회 자체가 실패할 때는 별도 fail-open 경로가 있어, 위 사전 분기가 모든 근거 없는 답변을 완전하게 차단한다고 주장할 수 없습니다. 근거 여부 확인과 생성 후 평가도 서로 다른 보호 장치입니다.

## 3. 출시 전 검증의 경계

- 문서 근거와 DB 기반 동적 결과를 같은 방법으로 평가할 수 없으므로 검증 기준을 구분했습니다.
- 인프라 배포 성공과 상담 업무 시나리오의 최종 수용 여부를 분리했습니다.
- 이 사례는 **Java/Spring 기반 사내 STG 파일럿의 설계·회귀 검증 기록**입니다. 공개 코드, 외부 제3자 검증, production 운영 성과와 동일시하지 않습니다.

## 배운 점

LLM이 사실을 말할 능력과 업무 권한을 결정할 능력은 별개입니다. 권한은 명시적인 서버 계약으로, 답변 신뢰도는 근거 검증과 평가로 다뤄야 합니다.
